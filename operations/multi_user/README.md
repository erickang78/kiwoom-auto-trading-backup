# 사용자별 독립 운영 환경 준비

## 현재 구조와 선택

현재 `/opt/kiwoom` 인스턴스는 한 명의 계좌용이다. 대시보드 접속 키, 키움 인증정보, 매매 상태 DB, 자동매매 프로세스가 모두 한 세트이며 로그인 세션에 사용자 ID가 없다. 기존 접속 키를 사람별로 나누는 방식으로는 계좌를 분리할 수 없다.

서버를 사용자별로 따로 만들 필요는 없다. 선택한 방향은 **기존 Lightsail 서버를 공유하되 사용자별 파일·프로세스 격리**이다. 키·계좌·DB·프로세스·도메인·백업을 분리한다. 실제 구현 순서와 2026-10-04 서버 용량 진단은 `SHARED_SERVER.md`에 기록했다. 준비가 완료되기 전에는 현재 운영 인스턴스 `example-server`에 신규 사용자 계좌를 연결하지 않는다.

AWS 서버 스냅샷은 디스크와 그 안의 인증정보 및 거래 DB도 복사한다. 기존 운영 서버 스냅샷을 신규 사용자 환경의 시작 이미지로 사용하지 않는다. 비밀정보가 없는 코드·이미지에서 설치한다.

## 신규 사용자 1명 등록 순서

1. 사용자별 HTTPS 호스트 이름과 격리된 앱 실행 환경을 만든다. 같은 서버를 쓰면 사용자별 컨테이너/볼륨/프로세스를, 별도 서버를 쓰면 사용자별 Lightsail 인스턴스를 준비한다. 기존 SSM 배포 IAM 정책을 함부로 확장하지 않는다. 서버를 공유하는 경우 SSM은 호스트 전체를 수정할 수 있으므로 사용자 격리는 앱 배포 절차에서도 강제해야 한다.
2. 이 저장소에서 배포할 코드를 검토해 개인 사진, 계좌 표시, 고정 URL을 제거하고 신규 도메인으로 설정한다. `python3 operations/multi_user/preflight.py --root <후보 경로> --origin https://<신규 도메인>`이 통과할 때까지 배포하지 않는다. 현재 `server-baseline`은 운영 복구 원본이므로 이 검사에 통과하지 않는 것이 정상이다.
3. 신규 사용자에게 본인 명의 키움 계좌와 REST API 이용 신청·인증정보 발급을 안내한다. 인증정보와 신규 대시보드 키는 **그 사용자 전용 비밀 저장 경로에만** 저장한다. 채팅, GitHub, 공용 파일, 다른 사용자 실행 환경으로 전달하지 않는다. 키움 API 이용 자격과 다계좌·자동매매 허용 범위는 해당 사용자의 계약과 공식 안내를 확인한다.
4. 신규 실행 환경에서 계좌 조회만 먼저 연결한다. 로그인한 화면의 계좌 식별자와 키움 API 조회 계좌가 일치하는지 검증한다. 다른 사용자의 계좌·거래 DB가 조회되지 않는지 확인한다.
5. 신규 사용자 전용 DB와 백업 대상, 복구 키, 백업 상태 표시를 구성한다. 기존 사용자의 DB 백업과 복구 경로를 공유하지 않는다. 복구 시험도 사용자별로 수행한다.
6. 가상매매만 켜고 주문 전송은 비활성화한다. 신호, 예산, 주문 미체결 조회, 중지·재시작, 알림을 확인한다. 실전 주문을 허용하기 전에는 해당 사용자 계좌와 주문 권한을 다시 대조한다.

## 완료 판정

- 사용자 A의 로그인 세션으로 B의 계좌·주문·거래 기록을 볼 수 없고, 반대 방향도 같다.
- 한 사용자의 매매 중지·재시작·예산 변경이 다른 사용자의 서비스에 영향을 주지 않는다.
- 서버 파일, 비밀정보, 거래 DB, 백업 및 복구 키가 사용자별로 분리돼 있다. 배포 권한이 호스트 전체를 건드릴 수 있는 경우 배포 도구가 정확한 사용자 환경만 변경한다.
- 신규 사용자 인스턴스의 계좌 조회와 백업 복구 시험이 끝나기 전에는 실전 주문 서비스를 시작하지 않는다.

한 백엔드 프로세스와 한 DB에 여러 계좌를 섞는 방식은 별도의 사용자 인증, 모든 API·DB·주문 경로의 테넌트별 권한 검증, 통합 테스트가 필요하다. 파일럿에서는 같은 서버를 쓰더라도 실행 환경과 DB를 사용자별로 분리한다.
