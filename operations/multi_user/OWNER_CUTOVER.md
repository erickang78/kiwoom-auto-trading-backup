# 기존 1인 운영 환경의 로그인 전환

현재 운영자의 계좌·거래 DB·매매 서비스·API 포트·대시보드 파일은 그대로 둔다. `/opt/kiwoom/dashboard_gateway.py` 한 파일만 초대 로그인 호환 게이트웨이로 전환하고 `/opt/kiwoom/tenant_auth.py` 및 일회성 이행 도구를 설치한다. 새로운 로그인 비밀번호는 기존 대시보드 접속 키와 동일하다. 이행 도구는 해당 값을 읽어서 salt가 있는 해시로만 저장하며, 값을 출력하거나 Git에 넣지 않는다. 기존 세션 쿠키는 새 게이트웨이에서 유효하지 않으므로 운영자는 다시 로그인해야 한다.

배포 전에는 서버의 실제 게이트웨이 해시가 감사에서 확인된 `a00d93ce46150a0fa61bd15bb2f66137df1f43d8fd31c7e2be366988f5d666a8`인지 다시 비교한다. 달라졌다면 중단하고 새 차이를 검토한다. 현재 운영 게이트웨이에만 있는 `/v1/backup/status`와 대시보드 백업 상태 스크립트 삽입은 새 게이트웨이에서 유지한다. `backend` API와 매매 워커 코드는 교체하지 않는다.

1. 현재 게이트웨이 원본과 systemd 상태를 서버 내부의 권한 700 백업 디렉터리에 저장한다. 원본은 외부로 복사하지 않는다.
2. 새 인증 모듈을 임시 경로에 설치해 컴파일한다. 기존 키와 `bootstrap_owner.py`로 사용자 인증 DB를 만든다. DB와 세션 서명 키의 소유자는 `ubuntu`, 권한은 600이어야 한다.
3. 새 게이트웨이를 임시 포트에서 띄워 로그인 페이지·미인증 API 차단·인증 후 대시보드·백업 상태·API 프록시를 확인한다. 키나 계좌 데이터를 출력하지 않는다.
4. 검증한 게이트웨이로 원자적 교체 후 `moa-dashboard.service`만 재시작한다. `moa-auto-trading.service` 등 주문 관련 서비스는 건드리지 않는다.
5. 외부 HTTPS 로그인 페이지와 서버 내부 인증 후 주요 GET API를 점검한다. 실패하면 즉시 보관한 원본 게이트웨이로 되돌리고 게이트웨이 서비스만 재시작한다. 새 인증 DB는 보존해도 원래 로그인 방식에는 사용되지 않는다.

추가 사용자의 서비스·Caddy 호스트·인증정보·거래 DB는 이번 전환에서 생성하거나 시작하지 않는다. 장중 동시 사용자와 계좌 간 접근 차단은 이후 별도로 시험한다.
